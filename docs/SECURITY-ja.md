# セキュリティ

## ロールとアクセス制御

| 操作 | Admin | Operator | Reviewer | Viewer |
| --- | --- | --- | --- | --- |
| 資産・脆弱性の閲覧 | 可 | 可 | 可 | 可 |
| 資産の登録・変更 | 可 | 可 | 不可 | 不可 |
| 脆弱性通報の登録 | 可 | 可 | 不可 | 不可 |
| 更新計画の作成・承認前の編集 | 可 | 可 | 不可 | 不可 |
| 高リスク変更の承認 | 不可 | 不可 | 可 | 不可 |
| 変更の実施記録 | 条件付き | 可 | 不可 | 不可 |
| 作業記録の追加・訂正の追記 | 可 | 可 | 不可 | 不可 |
| 障害の登録・変更 | 可 | 可 | 可 | 不可 |
| 監査の閲覧 | 可 | 可 | 可 | 可 |
| ユーザー・ロールの管理 | 可 | 不可 | 不可 | 不可 |
| システム設定（`/settings/system`）の閲覧・運用ルールの変更 | 可 | 不可 | 不可 | 不可 |

表の列は単独ロールを表します。システム設定はコンテナの環境変数と Laravel の設定ファイルで管理し、Admin の設定画面ではユーザーと固定ロールを扱います。高リスク変更の開始は、明示的に Operator が付与された指定担当者に限ります。Admin 権限のみでの承認や高リスク変更の開始は拒否します。

Reviewer は発起人や実施担当者と異なる必要があります。Operator と Reviewer を兼ねる場合は、Admin が付与者・理由・変更承認の範囲を記録します。判断時には有効な付与記録と実際のログインユーザーを照合します。DB の `change_approvals` の CHECK でも、自分が発起または実施を担当する計画の承認を拒否します。

Reviewer のチェック項目の免除は理由と範囲を記録する操作です。既存の合格の証拠を変更する操作は許可されません。直接 HTTP リクエストもサーバー側の Policy と操作ごとの権限判定を通ります。全体を許可する `Gate::before` は禁止しています。

## 追記専用の二重保護

1. `WorkRecord` と `AuditEvent` は Eloquent の `updating` と `deleting` で例外を投げます。WorkRecord の訂正は元の ID を参照する新しい行です。
2. 権限を分離するデプロイでは、アプリ用の MariaDB アカウントに `work_records` と `audit_events` の `SELECT` と `INSERT` のみを付与します。マイグレーションと Seeder は別の管理用アカウントで実行します。アプリ用アカウントへのスキーマ全体の `UPDATE`、`DELETE`、`ALL PRIVILEGES` や、同等の権限を含むロール付与を避け、その他のテーブルに必要な権限は個別に付与します。

DB 管理者が実行する付与例です。接続元とアカウント名は配備先に合わせます。

```sql
GRANT SELECT, INSERT ON soloops.work_records TO 'soloops_runtime'@'app_host';
GRANT SELECT, INSERT ON soloops.audit_events TO 'soloops_runtime'@'app_host';
```

実行用アカウントで接続し、`SHOW GRANTS` でテーブル権限と継承権限を確認します。検証用 DB では両テーブルで `SELECT` とトランザクション内の `INSERT` が通り、`UPDATE ... WHERE 1 = 0` と `DELETE ... WHERE 1 = 0` は権限不足になることを確かめます。

同梱のローカル Compose では、MariaDB の初期化時に作成する同じ DB ユーザーでアプリの実行・マイグレーション・Seeder を行います。Eloquent の保護は有効であり、DB アカウントの権限分離は上記の構成を別途適用したときに有効になります。

## 入力と認証情報

状態、関連 ID、必須項目はサーバー側で検証します。Blade の HTML エスケープと Eloquent またはクエリビルダーのパラメータ束縛を使います。変更を伴うフォームは CSRF 検証を通し、ログイン時にセッションを再生成します。セッションが有効でなくなったユーザーは再認証が必要です。

アプリのログインパスワードは安全なハッシュとして保存します。SSH 秘密鍵、接続用パスワード、API トークン、シークレットを業務テーブル、作業メモ、監査の記録対象、公開リポジトリに含めません。DB の接続設定とデモアカウントの初期値はローカルの `.env` から供給します。`.env.example` の秘密値は空欄です。外部サポート欄には架空の連絡先と参照番号を表示します。

## デモと CI の認証

`demo-admin`、`demo-operator`、`demo-reviewer`、`demo-viewer` はローカルの架空アカウントです。Seeder は指定された `DEMO_*_PASSWORD` をハッシュ化し、変数が未設定の場合は該当アカウントの作成を見送ります。公開のデモに共通パスワードを配布する運用は想定していません。 [Demo Accounts](../README.md#10-demo-accounts)

GitHub Actions に記載する DB のパスワードは、各ジョブで生成・破棄されるサービスコンテナだけで使う使い捨ての値です。ローカルや配備先のパスワード、デモアカウントの初期値とは別に扱います。CI ではテスト専用の DB に対してマイグレーションと検証を実行します。 [CI 定義](../.github/workflows/ci.yml)
